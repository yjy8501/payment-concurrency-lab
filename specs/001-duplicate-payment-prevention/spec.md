# Feature Specification: 이중 결제 방지 실험

**Feature Branch**: `001-duplicate-payment-prevention`

**Created**: 2026-10-13

**Status**: Draft

**Input**: User description: "같은 결제 승인 알림이 동시에 여러 번 와도 승인은 정확히 1번만 처리한다. 다섯 가지 처리 방식을 같은 조건에서 비교하고, PG 응답을 받지 못한 결제는 거래조회로 결과를 확정한다."

## User Scenarios & Testing *(mandatory)*

이 기능의 사용자는 **결제 시스템을 검토하는 개발자**다. 결제대행사(PG)는 가짜 PG로 재현한다.

### User Story 1 - 중복 승인 알림을 받아도 승인은 1번 (Priority: P1)

PG가 같은 결제의 승인 알림을 동시에 100번 보낸다. 시스템은 결제를 정확히 1번만 승인하고,
나머지 99번에는 오류 없이 「이미 처리됨」으로 응답한다.

**Why this priority**: 이중 승인은 고객에게 돈을 두 번 받는 사고로 이어진다. 이 실험의 핵심 목적이다.

**Independent Test**: 대기 상태 결제 1건을 만들고 같은 승인 알림 100개를 동시에 보낸 뒤,
승인 기록 수와 응답 종류를 센다.

**Acceptance Scenarios**:

1. **Given** 대기 상태인 결제 1건, **When** 같은 승인 알림 100개가 동시에 도착하면,
   **Then** 결제는 승인 상태가 되고 승인 기록은 정확히 1건이다.
2. **Given** 1번 시나리오와 같은 조건, **When** 100개 요청이 모두 끝나면,
   **Then** 1개는 「승인 완료」, 99개는 「이미 처리됨」으로 응답하고 오류 응답은 0개다.
3. **Given** 이미 승인된 결제, **When** 같은 승인 알림이 다시 도착하면,
   **Then** 승인 기록은 늘어나지 않고 「이미 처리됨」으로 응답한다.

---

### User Story 2 - 다섯 가지 처리 방식 비교 (Priority: P2)

검토자는 같은 조건(대기 결제 1건, 동시 알림 100개)에서 다섯 가지 처리 방식을 실행하고,
방식마다 승인 기록 수·「이미 처리됨」 응답 수·오류 응답 수·처리 시간을 표로 비교한다.

| 방식 | 설명 | 예상 결과 |
|---|---|---|
| ① 조회 후 저장 | 상태를 읽고, 대기면 승인으로 바꿔 저장 | 승인 기록이 여러 건 생길 수 있음 |
| ② 버전 충돌 감지 | 저장할 때 다른 요청이 먼저 바꿨으면 실패 처리 | 승인 1건, 일부 요청은 오류로 응답 |
| ③ 만료 시간이 있는 외부 잠금 | 잠금을 얻은 요청만 처리, 잠금은 일정 시간 뒤 자동 해제 | 평소에는 승인 1건(잠금 실패는 오류), 처리가 잠금 시간보다 길면 중복 발생 |
| ④ 조건부 상태 전이 + 승인 1건 제약 | 「대기일 때만 승인으로」 바꾸고, 결제당 승인 기록은 1건만 허용 | 승인 1건, 나머지는 「이미 처리됨」 |
| ⑤ 행 잠금 후 처리 | 결제를 읽을 때 잠가서 다른 요청은 기다리게 한 뒤 처리 | 승인 1건, 나머지는 「이미 처리됨」. 대신 잠금을 기다리는 시간이 생김 |

**Why this priority**: 「왜 이 방식을 골랐는가」에 대한 답을 측정 결과로 보여준다. 단, P1이 먼저 동작해야 의미가 있다.

**Independent Test**: 방식을 바꿔 가며 User Story 1과 같은 테스트를 실행하고 결과를 표로 모은다.

**Acceptance Scenarios**:

1. **Given** 다섯 가지 방식, **When** 각 방식으로 같은 조건의 테스트를 실행하면,
   **Then** 방식별 승인 기록 수·「이미 처리됨」 수·오류 수·처리 시간이 기록된다.
2. **Given** 방식 ①, **When** 테스트를 반복 실행하면,
   **Then** 승인 기록이 2건 이상 생기는 경우가 1회 이상 관찰된다.
3. **Given** 방식 ②, **When** 테스트를 반복 실행하면,
   **Then** 모든 실행에서 승인 기록이 정확히 1건이고, 오류 응답이 1개 이상 생긴다.
4. **Given** 방식 ③, **When** 처리 시간이 잠금 유지 시간보다 길어지도록 설정하면,
   **Then** 승인 기록이 2건 이상 생긴다.
5. **Given** 방식 ④와 ⑤, **When** 테스트를 반복 실행하면,
   **Then** 모든 실행에서 승인 기록이 정확히 1건이고 오류 응답이 0개다.

### User Story 3 - 응답을 못 받은 결제는 거래조회로 확정 (Priority: P3)

시스템은 결제를 「승인 요청 중」으로 먼저 바꾼 뒤 PG에 승인을 요청한다. 그런데 3초 안에 응답이 오지 않는다. 시스템은 이 결제를
「결과 모름」으로 보고, 대기가 끝나자마자 PG에 거래조회를 한다. 결과가 없으면 1초 간격으로
2번 더(총 3번) 조회한다. 끝까지 확정하지 못하면 「확인 필요」 상태로 두어 사람이 확인하게 한다.

**Why this priority**: 실제 결제에서는 응답 유실이 흔하다. 다만 P1·P2와 독립적으로 보여줄 수 있는 확장 시나리오다.

**Independent Test**: 가짜 PG가 응답을 지연·유실하도록 설정하고, 거래조회 결과에 따라 결제 상태가 어떻게 확정되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** PG가 승인 요청에 바로 「승인」으로 응답하는 결제, **When** 승인을 요청하면,
   **Then** 결제는 승인 상태가 되고 승인 기록은 1건이다.
2. **Given** PG가 승인 요청에 바로 「실패」로 응답하는 결제, **When** 승인을 요청하면,
   **Then** 결제는 실패 상태가 된다.
3. **Given** PG가 승인 요청에 3초 넘게 응답하지 않고 실제로는 승인한 결제,
   **When** 거래조회가 「승인」을 돌려주면, **Then** 결제는 승인 상태가 되고 승인 기록은 1건이다.
4. **Given** PG가 응답하지 않고 실제로는 승인하지 않은 결제,
   **When** 거래조회가 「실패」를 돌려주면, **Then** 결제는 실패 상태가 된다.
5. **Given** 거래조회도 계속 결과를 주지 않는 결제,
   **When** 3번 조회해도 결과가 없으면, **Then** 결제는 「확인 필요」 상태가 된다.
6. **Given** 거래조회 중인 결제, **When** 같은 결제의 승인 알림이 동시에 도착하면,
   **Then** 승인 기록은 정확히 1건이다.
7. **Given** 대기 상태인 결제 1건, **When** 같은 결제의 승인 요청이 동시에 10번 들어오면,
   **Then** PG에는 승인 요청이 1번만 나가고, 나머지 9번은 「이미 요청됨」으로 거절된다.

---

### Edge Cases

아래 예외 상황은 채택 방식(④)과 PG 승인 흐름(US3)에 적용한다.

- 승인 알림과 실패 알림이 같은 결제에 동시에 도착하면? → 먼저 반영된 결과 하나만 인정하고, 늦게 온 알림은 「이미 처리됨」으로 응답한다.
- 존재하지 않는 결제의 알림이 오면? → 「결제 없음」으로 응답하고 아무것도 바꾸지 않는다.
- 알림의 금액이 결제 금액과 다르면? → 승인하지 않고 「금액 불일치」로 응답한다.
- 「확인 필요」 상태인 결제에 승인 알림이 오면? → 승인으로 확정한다(승인 기록 1건).
- 처리 도중 시스템 오류가 나면? → 상태와 승인 기록이 함께 바뀌거나 둘 다 바뀌지 않는다(반쪽 반영 없음).

## Requirements *(mandatory)*

### Functional Requirements

FR-004·FR-005는 채택 방식(④)과 PG 승인 흐름(US3)에 적용한다. 방식 ①②③은 비교를 위해 일부러 이 요구사항을
지키지 않는 방식이며, 그 결과를 측정하는 것이 US2의 목적이다.

- **FR-001**: 시스템은 결제를 「대기」 상태로 생성할 수 있어야 한다(MUST).
- **FR-002**: 결제 상태는 「대기」, 「승인 요청 중」, 「승인」, 「실패」, 「확인 필요」 다섯 가지이며, 허용되는 변경은 다음뿐이다(MUST).
  대기 → 승인 요청 중 / 대기·승인 요청 중·확인 필요 → 승인 / 대기·승인 요청 중·확인 필요 → 실패 / 승인 요청 중 → 확인 필요.
- **FR-003**: 시스템은 PG의 승인·실패 알림을 받아 결제 상태를 바꿔야 한다(MUST).
- **FR-004**: 한 결제에 대한 승인 기록은 어떤 경우에도 최대 1건이어야 한다(MUST).
- **FR-005**: 이미 처리된 결제에 대한 알림에는 오류가 아닌 「이미 처리됨」으로 응답해야 한다(MUST).
- **FR-006**: 상태 변경과 승인 기록 생성은 함께 반영되거나 함께 취소되어야 한다(MUST).
- **FR-007**: 시스템은 다섯 가지 처리 방식(①~⑤)을 각각 선택해 실행할 수 있어야 한다(MUST).
- **FR-008**: 시스템은 방식별로 승인 기록 수, 「이미 처리됨」 응답 수, 오류 응답 수, 전체 처리 시간, 평균 응답 시간을 측정할 수 있어야 한다(MUST).
- **FR-009**: PG 승인 요청은 3초 안에 응답이 없거나 호출이 오류로 끝나면 「결과 모름」으로 처리해야 한다(MUST).
- **FR-010**: 「결과 모름」 결제는 대기가 끝나자마자 거래조회를 하고, 결과가 없으면 1초 간격으로 2번 더(총 3번) 조회해 승인·실패를 확정해야 한다(MUST).
- **FR-011**: 3번 조회해도 확정하지 못하면 결제를 「확인 필요」 상태로 바꿔야 한다(MUST).
- **FR-012**: 가짜 PG는 정상 응답(승인·실패), 응답 지연(지정한 시간 뒤 응답), 응답 유실, 호출 오류, 거래조회 결과(승인·실패·결과 없음)를 설정할 수 있어야 한다(MUST).
- **FR-013**: 시스템은 PG에 승인을 요청하기 전에 결제를 「승인 요청 중」으로 먼저 바꿔야 하며, 이 변경에 성공한 요청만 PG를 호출해야 한다(MUST).
  같은 결제의 승인 요청이 동시에 여러 번 와도 PG 승인 요청은 1번만 나가야 한다.

### Key Entities

- **결제**: 주문 하나에 대한 결제. 결제 번호, 금액, 상태(대기·승인 요청 중·승인·실패·확인 필요)를 가진다.
- **승인 기록**: 결제가 승인되었다는 사실. PG 거래 번호, 승인 금액, 승인 시각을 가지며 결제당 최대 1건이다.
- **PG 알림**: PG가 보내는 결제 결과. 결제 번호, PG 거래 번호, 결과(승인·실패), 금액을 담는다.
- **거래조회 결과**: 시스템이 PG에 물어본 결제 결과. 승인·실패·결과 없음 중 하나다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 방식 ④에서 같은 승인 알림 100개를 동시에 보내는 테스트를 10번 반복하면, 10번 모두 승인 기록이 정확히 1건이다.
- **SC-002**: SC-001의 모든 실행에서 「이미 처리됨」 응답은 99개, 오류 응답은 0개다.
- **SC-003**: 다섯 가지 방식의 측정 결과(처리 시간 포함)가 한 표로 정리되고, 누구나 명령 한 번으로 같은 표를 다시 만들 수 있다.
- **SC-004**: 방식 ①과 ③에서 승인 기록이 2건 이상 생기는 경우를 테스트로 재현할 수 있다.
- **SC-005**: 응답을 받지 못한 결제는 승인 요청 후 약 5초(대기 3초 + 조회 간격 2초) 안에 승인·실패·확인 필요 중 하나로 확정되고, 대기 상태로 남는 결제는 0건이다.
- **SC-006**: 방식 ⑤도 10번 모두 승인 기록이 정확히 1건이고 오류 응답이 0개이며, 비교표에서 ④와 처리 시간을 나란히 비교할 수 있다.
- **SC-007**: 같은 결제에 승인 요청 10개를 동시에 보내면 PG 승인 요청은 정확히 1번 나가고, 승인 기록은 1건이다.

## Assumptions

- 사용자는 결제 시스템을 검토하는 개발자이며, 화면 없이 테스트와 결과 표로 확인한다.
- PG는 가짜 PG로 대신하며, 실제 PG 연동은 범위 밖이다.
- 환불, 부분 취소, 회원, 인증, 화면은 범위 밖이다.
- 반복 실행 횟수(10번)는 동시성 결과가 우연이 아님을 보이기 위한 기본값이다.
- 「확인 필요」 결제를 사람이 처리하는 화면·절차는 만들지 않는다. 상태로 남기는 데까지가 범위다.
- 방식 ②의 버전 충돌과 방식 ③의 잠금 획득 실패는 재시도·대기 없이 그대로 오류로 센다(방식 간 공정 비교를 위해).
- 처리 시간은 실행한 컴퓨터에 따라 달라지는 참고값이다. 방식 간 상대 비교에만 쓴다.
- 「승인 요청 중」으로 바꾼 뒤 서버가 멈춰 그 상태에 남은 결제를 복구하는 절차는 범위 밖이다.
