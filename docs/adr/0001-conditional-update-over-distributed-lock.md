# ADR 0001. 분산 락이 아니라 조건부 상태 전이 + 유일 제약으로 중복 승인을 막는다

- 상태: 채택
- 날짜: 2026-10-13
- 관련 문서: [spec](../../specs/001-duplicate-payment-prevention/spec.md), [research R3](../../specs/001-duplicate-payment-prevention/research.md)

## 배경

PG는 같은 결제의 승인 알림을 여러 번 보낼 수 있다. 네트워크 재시도, PG 쪽 재전송, 사용자 새로고침이
겹치면 같은 알림이 거의 동시에 여러 개 도착한다. 이때 승인이 두 번 반영되면 고객에게 돈을 두 번 받는 사고가 난다.

요구사항은 세 가지다.

1. 승인 기록은 결제당 정확히 1건 (FR-004)
2. 중복 알림에는 오류가 아니라 「이미 처리됨」으로 응답 (FR-005). 오류를 받은 PG는 알림을 다시 보내기 때문이다.
3. 상태 변경과 승인 기록은 함께 반영되거나 함께 취소 (FR-006)

## 결정

결제 상태 변경을 조건부 UPDATE 한 문장으로 처리하고, 승인 기록 테이블에 결제당 유일 제약을 건다.

```sql
UPDATE payment
   SET status = 'APPROVED'
 WHERE id = :id
   AND status IN ('PENDING', 'REQUESTING', 'NEEDS_REVIEW')
```

- 바뀐 행이 1이면 이번 요청이 처리한 것이다. 같은 트랜잭션에서 승인 기록을 저장한다.
- 바뀐 행이 0이면 다른 요청이 이미 처리한 것이다. 「이미 처리됨」으로 응답한다.
- 승인 기록 테이블의 `UNIQUE (payment_id)`는 코드가 잘못되어도 두 번째 기록을 막는 마지막 안전망이다.

PostgreSQL은 READ COMMITTED에서 같은 행을 바꾸려는 다른 UPDATE가 있으면 그 트랜잭션이 끝날 때까지 기다린 뒤
WHERE 조건을 다시 확인한다. 그래서 동시에 몇 개가 와도 1행을 바꾸는 요청은 하나뿐이다.
「확인」과 「변경」 사이에 다른 요청이 끼어들 틈이 없다.

구현: [`PaymentSettler`](../../src/main/kotlin/io/github/yjy8501/paymentlab/payment/PaymentSettler.kt),
[`ConditionalUpdateStrategy`](../../src/main/kotlin/io/github/yjy8501/paymentlab/callback/strategy/ConditionalUpdateStrategy.kt)

## 검토한 대안

다섯 방식을 같은 조건(대기 결제 1건, 동시 알림 100개, 10회 반복)으로 실제 PostgreSQL·Redis에서 측정했다.
전체 결과는 [README](../../README.md#결과)에 있다.

| 방식 | 승인 기록 | 이미 처리됨 (평균) | 오류 (평균) | 판단 |
|---|---|---|---|---|
| ① 조회 후 저장 | 12~27건, 10회 모두 중복 | 81.6 | 0 | 기각 |
| ② 버전 충돌 감지 (`@Version`) | 1건 | 78.9 | 20.1 | 기각 |
| ③ 만료 잠금 (Redis `SET NX PX`) | 1건 (TTL 만료 시 중복) | 1.9 | 97.1 | 기각 |
| ④ 조건부 전이 + 유일 제약 | 1건 | 99.0 | 0 | **채택** |
| ⑤ 행 잠금 (`SELECT ... FOR UPDATE`) | 1건 | 99.0 | 0 | 기각 (차선) |

### ① 조회 후 저장

상태를 읽고, 대기면 승인으로 바꿔 저장한다. 확인과 변경 사이에 틈이 있어서 동시에 대기 상태를 읽은
요청이 모두 승인 기록을 남긴다. 10회 모두 중복이 생겼고, 한 결제에 승인 기록이 최대 27건 생겼다.

### ② 버전 충돌 감지

중복 승인은 막는다. 하지만 진 요청은 커밋 단계에서 예외를 받고, 이 예외만으로는
「이미 처리됨」인지 「잠깐 겹쳤을 뿐 아직 처리 안 됨」인지 구분할 수 없다. 그래서 평균 20건이 오류(409)로 나갔다.
재시도를 붙이면 오류는 줄지만, 재시도 횟수·간격이라는 설정이 하나 더 생기고 결국 다시 조회해 상태를 확인해야 한다.
④는 같은 결과를 재시도 없이 낸다.

### ③ 만료 시간이 있는 Redis 잠금

평소에는 승인 1건을 지키지만 두 가지 문제가 있다.

1. **TTL이 지나면 잠금이 풀린다.** 처리 시간(0.3초)이 TTL(0.1초)보다 길면, 처리 도중 잠금이 풀리고
   PG가 다시 보낸 알림이 잠금을 새로 얻어 같은 결제를 또 승인한다. 이 상황을
   [`RedisLockExpiryTest`](../../src/test/kotlin/io/github/yjy8501/paymentlab/callback/RedisLockExpiryTest.kt)에서 재현했다.
   GC 멈춤, DB 지연, 네트워크 지연은 처리 시간을 언제든 TTL보다 길게 만들 수 있다.
2. **잠금을 못 얻은 요청은 오류다.** 평균 97.1건이 409를 받았다. 기다리게 하면 대기 시간과 TTL을 함께 조정해야 한다.

잠금 연장(watchdog)이나 펜싱 토큰으로 보완할 수 있지만, 그러면 결국 「DB에 쓸 때 조건을 확인한다」는
④와 같은 장치가 필요하다. 지켜야 할 것이 DB의 결제 행 하나라면, DB 밖에 잠금을 하나 더 두는 것은
Redis라는 장애 지점과 TTL이라는 설정만 늘린다.

### ⑤ 행 잠금

④와 똑같이 정확하다(승인 1건, 이미 처리됨 99, 오류 0). 차이는 기다리는 방식이다.
⑤는 요청들이 결제 행 잠금을 차례로 기다리며 각자 조회·변경을 한다. 이번 측정에서 전체 처리 시간은
⑤가 평균 27ms, ④가 평균 21ms였다. 처리 내용이 단순해서 차이가 작지만, 잠금을 잡은 채로 하는 일이
길어질수록 대기 시간이 함께 늘어난다. ④는 잠금이 UPDATE 한 문장 동안만 유지된다.

## 결과

좋은 점

- 100개 동시 알림에서 10회 모두 승인 1건, 이미 처리됨 99건, 오류 0건 (SC-001·002)
- 추가 인프라(Redis)나 재시도 설정이 필요 없다
- 같은 확정 로직을 PG 거래조회 흐름(US3)에서도 쓴다. 거래조회와 알림이 겹쳐도 승인 1건이다

주의할 점

- DB가 「UPDATE가 조건을 다시 확인한다」는 성질에 기대고 있다. PostgreSQL READ COMMITTED에서 확인했다.
  다른 DB나 격리 수준으로 옮길 때는 같은 테스트로 다시 확인해야 한다.
- 외부 호출(PG 승인 요청)은 DB 트랜잭션으로 되돌릴 수 없다. 그래서 이 저장소의 승인 요청 API는 호출 **전에**
  같은 조건부 전이(`PENDING → REQUESTING`)로 권리를 선점한다. 문서 검토 중 이 구멍을 발견했고, 수정 전에는
  동시 요청 10개가 PG를 10번 호출하는 것을 테스트로 재현한 뒤 고쳤다 (FR-013, SC-007).
  다만 선점한 뒤 서버가 멈추면 결제가 「승인 요청 중」에 남으므로, 운영에서는 이를 찾아 거래조회하는 복구 작업이 필요하다.
- 여러 저장소나 서비스에 걸친 작업(결제 승인과 다른 서비스의 포인트 차감 등)은 DB 트랜잭션 하나로 묶이지 않는다.
  그때는 보상 처리, 아웃박스, 멱등성 키를 함께 검토한다.
