# ADR 0002. 실험용 승인 기록 테이블을 따로 둔다

- 상태: 채택
- 날짜: 2026-10-13
- 관련 문서: [research R4·R5](../../specs/001-duplicate-payment-prevention/research.md), [plan Complexity Tracking](../../specs/001-duplicate-payment-prevention/plan.md#complexity-tracking)

## 배경

이 저장소는 다섯 가지 처리 방식이 실제로 몇 번 승인하는지 세는 실험이다.
그런데 정답 방식(④)의 핵심 중 하나는 승인 기록 테이블의 `UNIQUE (payment_id)`다.
모든 방식이 이 테이블에 쓰면 ①처럼 중복 승인을 하는 방식도 두 번째 기록부터 제약 위반 오류가 나서,
「몇 번 승인하려 했는지」가 「오류 몇 건」으로 바뀌어 버린다.

## 결정

- 승인 기록 테이블을 두 개 둔다. 열 구성은 같다.
  - `approval`: `UNIQUE (payment_id)`가 있다. ④와 PG 승인 흐름이 쓴다.
  - `approval_unguarded`: 유일 제약이 없다. ①②③⑤가 쓴다.
- 결제 테이블은 하나지만 엔티티를 두 개 매핑한다.
  - `Payment`: 버전 검사 없음. ①③④⑤가 쓴다.
  - `VersionedPayment`: `@Version`이 있다. ②만 쓴다.

## 검토한 대안

- **테이블 하나에 모든 방식이 기록**: 중복이 제약 위반으로 가려진다. 원칙 III(실패도 보여주기)에 어긋나 기각.
- **방식별로 스키마를 따로 둔다**: 비교는 공정하지만 마이그레이션·설정이 다섯 배가 된다. 원칙 VI(단순하게)에 어긋나 기각.
- **엔티티 하나에 `@Version`**: ①③⑤에도 낙관적 락이 걸려 방식이 섞인다. 기각.

## 결과

- ①은 실제로 12~27건까지 승인 기록을 남겨 중복이 숫자로 드러난다.
- ⑤는 유일 제약 없이도 1건임을 보여준다. 정확성이 제약이 아니라 잠금에서 나온다는 뜻이다.
- 운영 코드라면 `approval_unguarded`는 존재하지 않는다. 실험을 위한 테이블임을 마이그레이션 주석에 적었다.
